# 배포 — Railway

C:road 를 Railway 에 올리는 절차. 처음 한 번은 이 문서를 위에서 아래로 따라가면 된다.

> **왜 Railway 인가** — C:road 는 MySQL 을 쓴다. Railway 는 MySQL 을 서비스로 붙여
> 주고 접속 정보를 환경변수로 주입해 준다. 앱과 DB 를 한 프로젝트에서 관리할 수 있어
> 학생 프로젝트 규모에서 손이 가장 적게 든다.

## 1. 앱 서비스 만들기

1. [railway.app](https://railway.app) → **New Project → Deploy from GitHub repo** → `C:road`
2. **Settings** 에서 다음을 지정한다.

| 항목 | 값 | 이유 |
|---|---|---|
| **Root Directory** | **비워 둔다 (저장소 루트)** | 아래 참고 |
| **Build Command** | `npm run build` | DART 기업 색인(11만 건·6MB)을 받는다. 아래 참고 |
| **Start Command** | `npm start` | 루트 `package.json` 이 `backend/src/server.js` 를 띄운다 |

> **Build Command 는 왜 필요한가** — 기업분석이 쓰는 `backend/data/dart-corps.json`
> 은 **깃에 없다**(6MB 짜리가 받을 때마다 히스토리에 쌓인다). 우리가 만든 자료가
> 아니라 DART 가 매일 주는 원본이라 빌드에서 받는다.
>
> Nixpacks 는 `package.json` 에 `build` 가 있으면 자동으로 돌리므로 대개 비워 둬도
> 되지만, **명시해 두는 편이 안전하다**(빌더가 바뀌면 조용히 안 돌고, 화면에서는
> "DART 가 자료를 안 준다"로만 보인다).
>
> `DART_API_KEY` 가 **빌드 시점에** 있어야 한다(3번에서 넣는다. Railway 는 서비스
> 변수를 빌드에도 준다). 키가 없거나 DART 가 죽어 있으면 **건너뛰고 배포는 계속된다**
> — 기업분석의 개요·재무·경쟁사 칸만 비고 나머지는 멀쩡하다. 부팅 로그의
> `[기능] … 기업분석` 에 어느 쪽인지 찍힌다.

> **Root Directory 를 `backend` 로 두면 안 된다.** 서버 코드는 `backend/` 에 있지만
> 저장소 밖이 아니라 **위쪽**을 참조한다.
>   - `routes/casAnalyze.js` 가 `frontend/js/cas.js` 를 읽는다 (배점 상수의 단일 출처)
>   - `server.js` 가 `express.static` 으로 `frontend/` 를 통째로 서빙한다
>
> 실제로 `backend` 로 뒀다가 이렇게 죽었다:
> `Error: Cannot find module '../../../frontend/js/cas.js'`.
> 설령 이 require 를 없애도 화면이 통째로 안 뜬다 — 프론트엔드가 이미지에 없기 때문이다.
>
> 루트 `package.json` 은 npm **workspaces** 로 `backend` 를 물고 있어서,
> 루트에서 `npm ci` 한 번이면 백엔드 의존성까지 설치된다.

Node 버전은 루트 `package.json` 의 `engines` 에서 읽는다(`>=20`).

첫 배포는 **실패해도 정상이다** — DB 가 아직 없어서 연결에 실패하고 서버가 죽는다
(일부러 그렇게 만들었다. 자세한 이유는 아래 '알려진 것들').

## 2. MySQL 서비스 추가

**New → Database → Add MySQL**

같은 프로젝트에 붙이면 Railway 가 `MYSQL_URL` 을 만들어 준다. 앱 서비스의
**Variables** 에서 그 값을 참조하도록 연결한다(`${{MySQL.MYSQL_URL}}`).

`src/mysql.js` 가 `MYSQL_URL` 을 먼저 보고, 없으면 `DB_HOST`/`DB_USER`/… 를 쓴다.
그래서 **배포에서는 MYSQL_URL 하나면 되고 로컬은 지금 방식 그대로**다.

---

## 3. 환경변수

앱 서비스의 **Variables** 에 넣는다. 로컬 `.env` 를 옮기되 아래를 **추가·수정**한다.

| 변수 | 값 |
|---|---|
| `MYSQL_URL` | `${{MySQL.MYSQL_URL}}` (2번에서 연결) |
| `NODE_ENV` | `production` |
| `ALLOWED_ORIGINS` | `https://<배포도메인>` |
| `OAUTH_REDIRECT_BASE` | `https://<배포도메인>` |

그대로 옮길 것: `DART_API_KEY`(**빌드에서 쓴다** — 1번 참고) ·
`DATA_GO_KR_SERVICE_KEY` · `GROQ_API_KEY` · `CAS_AI_PROVIDER` ·
`NAVER_CLIENT_ID/SECRET`(뉴스) · `NAVER_LOGIN_CLIENT_ID/SECRET` ·
`KAKAO_REST_API_KEY` · `KAKAO_CLIENT_SECRET` · `TOSS_CLIENT_KEY` · `TOSS_SECRET_KEY`

**넣지 않을 것**: `PORT`(Railway 가 주입) · `DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`
(로컬 전용. `MYSQL_URL` 이 있으면 무시되지만 헷갈리니 두지 않는다)

## 4. 스키마와 데이터 넣기

MySQL 서비스의 **Connect** 탭에서 공개 접속 정보(`MYSQL_PUBLIC_URL`)를 복사해
**로컬에서** 실행한다. Railway 안에는 셸이 없다.

```bash
cd backend

# 1) 스키마 (테이블 13개)
MYSQL_URL="<MYSQL_PUBLIC_URL>" node scripts/load-schema.js
#   mysql CLI 를 쓰지 않는다 — Docker 로만 MySQL 을 돌리면 PATH 에 없다.
#   어느 DB 에 넣는지 먼저 찍고 시작하므로, 주소를 잘못 붙였으면 그때 끊으면 된다.

# 2) 카탈로그만 (자격증 643 · 학과 193 · 기업 6,634 · 직업 461)
MYSQL_URL="<MYSQL_PUBLIC_URL>" node scripts/migrate-to-mysql.js --catalog

# 3) 커리어 인사이트 편집 글 5편 + 운영방침 공지
#    **빠뜨리기 쉬운 단계다.** 이걸 안 돌리면 홈 첫 화면의 '커리어 인사이트'
#    카드 칸이 통째로 사라지고(home.js paintArticles 가 칸을 숨긴다), 게시판은
#    빈 목록으로 시작한다. 로컬에서만 돌려 두고 배포에서 잊는 일이 실제로 있었다.
MYSQL_URL="<MYSQL_PUBLIC_URL>" node scripts/seed-insights.js
MYSQL_URL="<MYSQL_PUBLIC_URL>" node scripts/seed-notice.js
```

두 시드 모두 **여러 번 돌려도 안전하다**(이미 있는 글은 건너뛴다). 글 내용을 고쳤을
때만 `node scripts/seed-insights.js --force` 로 덮어쓴다.

**회원 데이터는 옮기지 않는다** — 로컬 db.json 은 대부분 데모 시드이고 내 테스트
계정도 섞여 있다. 카탈로그만 넣고 실제 가입자를 받는다.

통계 화면에 표본이 필요하면 배포 후 백오피스에서 시드를 넣는다(7번 참고).

### 인사이트 글이 배포에 안 보일 때

증상은 하나다 — **홈에 '커리어 인사이트' 칸이 아예 없다.** 카드를 그리지 못하면
칸을 숨기도록 해 뒀기 때문이다(제목만 있고 안 열리는 카드보다 낫다는 판단).

```bash
# 배포 DB 에 글이 들어갔는지부터 본다
curl -s https://<배포주소>/api/insights/featured
```

`articles` 의 `postId` 가 전부 `null` 이면 시드를 안 돌린 것이다. 위 3) 을 실행한다.

## 5. 도메인 받고 콘솔에 등록

**Settings → Networking → Generate Domain** 으로 주소가 나온다
(`careerly-production-xxxx.up.railway.app`).

그 주소를 3번의 `ALLOWED_ORIGINS`·`OAUTH_REDIRECT_BASE` 에 채우고 **재배포**한 뒤,
각 콘솔에 콜백을 **추가** 등록한다. 로컬 주소는 지우지 말 것 — 개발할 때 계속 쓴다.

| 서비스 | 등록할 곳 | 값 |
|---|---|---|
| 네이버 | 애플리케이션 → API 설정 → 서비스 환경 | 서비스 URL `https://<도메인>`<br>Callback `https://<도메인>/api/auth/naver/callback` |
| 카카오 | 앱 설정 → 플랫폼 → Web | 사이트 도메인 `https://<도메인>` |
| 카카오 | 앱 설정 → 플랫폼 키 → **REST API 키** | 리다이렉트 URI `https://<도메인>/api/auth/kakao/callback` |

> 카카오는 로그인 **전에는** 리다이렉트 URI 를 검사하지 않는다. 등록이 틀려도 로그인
> 화면까지는 뜨고, 로그인한 뒤에야 `KOE006` 이 난다. 반드시 실제로 로그인해 봐야 안다.

> 스테이징(8장)을 만들면 **같은 표를 스테이징 도메인으로 한 번 더** 등록한다.
> 콘솔은 여러 개를 허용하므로 로컬·스테이징·운영 세 벌이 동시에 살아 있을 수 있다.

## 6. 배포 후 확인

```bash
curl https://<도메인>/api/health                 # {"ok":true}
curl https://<도메인>/api/auth/providers         # 네이버·카카오 둘 다 나오는지
curl https://<도메인>/api/payments/config        # {"enabled":true, clientKey:"test_ck_..."}
curl -s https://<도메인>/api/jobs | head -c 120  # 직업 분류(461) — 4번이 됐는지 확인
curl -s "https://<도메인>/api/certs/suggest?q=정보"        # 자격증 LIKE 검색
curl -s -o /dev/null -w "%{http_code}\n" https://<도메인>/api/admin/users   # 404 여야 정상
```

브라우저에서:
1. 네이버·카카오 로그인 → **추가입력 화면**이 뜨는지
2. 스펙 입력 → 저장 → 다시 열었을 때 자격증·활동이 그대로인지
3. 멘토 찾기 → 신청 → **결제창** (테스트 키라 돈은 안 나간다)
4. **재배포한 뒤 다시 로그인** → 계정이 살아있는지

열어 두는 것이라 권하지 않는다.)

## 8. 스테이징 환경 (팀 작업용)

혼자 쓸 때는 `main` 푸시 = 배포로 충분했다. **여럿이 고치기 시작하면 검증 안 된
코드가 곧바로 운영에 나간다.** 그래서 배포 대상 환경을 둘로 나눈다.

| 환경 | 브랜치 | 도메인 | DB |
|---|---|---|---|
| production | `main` | `careerly-production-5d6b.up.railway.app` | 운영 MySQL |
| staging | `dev` | (새로 발급) | **스테이징 전용 MySQL** |

Railway 프로젝트 → **Environments → New Environment** 로 `staging` 을 만들고,
production 과 **다르게** 둘 것만 아래에 적는다. 나머지(Root Directory 비움,
Start Command `npm start`, 키들)는 production 과 같다.

| 항목 | 값 |
|---|---|
| Source → Branch | `dev` |
| MySQL | **New → Database → Add MySQL 로 staging 안에 새로 만든다** |
| `MYSQL_URL` | `${{MySQL.MYSQL_URL}}` — **같은 환경 안의 서비스**를 가리켜야 참조가 풀린다 |
| `ALLOWED_ORIGINS` · `OAUTH_REDIRECT_BASE` | staging 도메인 |

> **staging 이 운영 DB 를 가리키면 안 된다.** 테스트 가입·테스트 결제가 운영
> 데이터에 섞이고, 스키마를 바꾸는 순간 운영이 같이 깨진다. 환경을 만든 직후
> staging 부팅 로그의 `[mysql] 연결됨` 호스트가 운영과 다른지 **눈으로 확인한다.**

스테이징 DB 채우기 — 4번과 같다. 주소만 staging 것을 쓴다:

```powershell
$env:MYSQL_URL = "<staging MySQL 의 MYSQL_PUBLIC_URL>"
cd backend
node scripts/load-schema.js
node scripts/migrate-to-mysql.js --catalog
node scripts/seed-insights.js   # 홈의 커리어 인사이트 카드가 이걸 본다
node scripts/seed-notice.js
Remove-Item Env:MYSQL_URL     # 반드시. 안 지우면 이후 로컬 작업이 원격 DB 를 건드린다
```

마지막으로 5번의 콜백을 staging 도메인으로 한 번 더 등록한다.

## 9. 2회차 이후 배포 (dev → main)

인프라는 이미 있다. 이 절차의 본체는 **순서**다.

1. **`dev` 에서 검증**
   ```bash
   for f in test/*.test.js; do node "$f" | tail -1; done   # 저장소 루트에서
   ```
   그리고 staging 도메인에 6번의 curl 점검을 돌린다. 부팅 로그의 `[기능]` 줄도 본다.
2. **스키마가 바뀌었으면 운영 DB 를 먼저 마이그레이션한다.** 코드 배포보다 앞이다 —
   순서를 뒤집으면 새 코드가 없는 컬럼을 읽는 구간이 생긴다.
   ```powershell
   $env:MYSQL_URL = "<production MYSQL_PUBLIC_URL>"
   cd backend
   node scripts/load-schema.js      # 새 테이블 (CREATE TABLE IF NOT EXISTS)
   node scripts/migrate-schema.js   # 새 컬럼·인덱스 (ALTER TABLE ADD)
   Remove-Item Env:MYSQL_URL
   ```
   **두 개를 다 돌린다.** `schema.sql` 은 전부 `CREATE TABLE IF NOT EXISTS` 라
   테이블이 이미 있으면 통째로 건너뛴다 — 새로 추가한 **컬럼은 영영 안 생기는데
   에러도 안 난다.** load-schema 는 '완료' 를 찍고 서버도 뜨고, 저장할 때가 되어서야
   `Unknown column '...' in 'field list'` 로 500 이 난다.

   **2026-09-02 운영에서 실제로 겪었다.** 빠져 있던 컬럼은 셋이었다 —
   `profiles.mentor_fields` · `user_specs.job_codes` · `spec_activities.star`.
   증상은 '멘토 찾기가 안 열린다' 와 '스펙 저장이 안 된다' 였는데, 둘 다 원인이 같다:
   `mentors.list()` 와 `specs.upsert()` 가 그 컬럼들을 **이름으로** 조회한다.
   `SELECT *` 인 조회(스펙 불러오기)는 멀쩡해서 '반은 되고 반은 안 되는' 상태였다.
   비로그인으로도 열리는 `GET /api/mentors` 가 배포에서만 500 이라 그걸로 좁혔다 —
   **로컬과 배포에 같은 공개 엔드포인트를 나란히 찔러 보는 것**이 가장 빨랐다. 컬럼은
   `migrate-schema.js` 가 넣는다 — 이미 있으면 건너뛰고 `DROP` 은 하지 않으니
   여러 번 돌려도 안전하다.

   새 컬럼을 추가했다면 `schema.sql` 과 `scripts/migrate-schema.js` 의 `COLUMNS`
   **양쪽에** 같은 정의로 적는다. 한쪽만 고치면 새 DB 와 기존 DB 의 스키마가 갈린다.
3. `dev` → `main` PR → 승인 → merge. **merge 가 곧 운영 배포다.**
4. **`Redeploy` 를 누르지 않는다.** 그 배포의 **옛 커밋**이 다시 올라간다. 코드를
   바꿨으면 푸시 이벤트를 기다리거나 `Deploy latest commit` 을 쓴다.
   `Redeploy` 는 **변수만 바꿨을 때** 쓰는 버튼이다. (작업정리 13-3 에서 가장 오래
   잡아먹은 함정)
5. 배포 후 운영 도메인에 6번 점검을 다시 돌린다. 결제는 밖에서 검증할 수 없으므로
   브라우저에서 **결제창 승인까지** 한 번 통과시킨다.
6. 문제가 있으면 Railway 배포 목록에서 **직전 배포로 Rollback** 한 뒤 원인을 찾는다.
   2번에서 DB 를 이미 바꿨다면 코드만 되돌아간다는 점을 기억할 것 — 그래서 스키마
   변경은 **되돌려도 옛 코드가 동작하는 형태**(컬럼 추가는 되고, 삭제·이름변경은
   위험)로 만든다.

## 10. 볼륨 — 배포 시간을 13분에서 1~2분으로 (2026-09-10)

### 왜

배포마다 `npm run build` 가 외부 자료 4종을 순차로 받고 있었다. 대부분이 **크롤링 예의를
지키느라 자는 시간**이다 — 고용24 238페이지 × 1.2초, 위비티 (30페이지 + 상세 80건) × 3초.
합계 **13~17분**, 그중 10분 남짓이 `sleep` 이었다.

근본 원인은 **디스크가 일회용**이라는 것이다. Railway 는 배포마다 컨테이너를 새로 만들어
갈아 끼우므로, 지난 배포 때 받아 둔 11MB 짜리 공고 캐시가 통째로 사라진다. 그래서 매번
처음부터 다시 받았다.

**볼륨은 컨테이너 밖에 붙는 디스크다.** 배포해도 안 지워지고 새 컨테이너에 다시 꽂힌다.
캐시가 살아남으면 `daily-refresh.js` 가 *"20시간 이내 자료라 그대로 씁니다"* 로 건너뛴다.

### 붙이는 곳이 중요하다 — `backend/data` 에 붙이면 서버가 깨진다

볼륨은 마운트한 경로의 **이미지 속 내용을 가린다.** 그런데 `backend/data` 에는 받아오는
파일만 있는 게 아니라 **깃으로 함께 배포되는 파일이 18개**(자격증·학과·업종분류·NCS 등
약 2MB) 들어 있다. 거기에 볼륨을 붙이면 그것들이 통째로 안 보여 서버가 그 자리에서 깨진다.

그래서 **받아오는 것만** `CACHE_DIR` 로 갈라 뒀다(`backend/src/cache-dir.js`).

| | 어디 | 무엇 |
|---|---|---|
| 깃으로 배포 | `backend/data` (이미지) | 자격증·학과·업종분류·NCS·표본 지표 … 18개 |
| 받아서 쌓임 | `CACHE_DIR` (볼륨) | dart-corps · work24-jobs · alio-jobs · wevity · logos/ · dart-report/ · wage-traits/ · posters/ |

### 설정 (Railway 콘솔)

1. 앱 서비스 → **Variables** → `CACHE_DIR=/data`
2. 앱 서비스 → **Settings → Volumes → New Volume**
   - **Mount path: `/data`** (위 변수와 **같은 값**이어야 한다)
   - 크기는 1GB 면 넉넉하다 — 받아오는 자료가 다 합쳐 18MB 이고 로고·보고서 캐시를
     더해도 한참 남는다
3. 재배포. 부팅 로그에서 확인한다:
   ```
   [cache] 받아오는 자료: /data (볼륨)
   ```
   `(볼륨 없음 — 재배포하면 다시 받습니다)` 가 찍히면 변수나 mount path 가 어긋난 것이다.

### 첫 배포 직후

볼륨은 **빈 채로** 붙는다. 그래서 첫 배포에서는 캐시가 없고, 서버가 부팅 30초 뒤부터
백그라운드로 받는다(`daily-refresh.js`, 부팅을 막지 않는다). 다 차기까지 7~10분 정도
공고·공모전·기업분석 칸이 빈다. **그 다음 배포부터는 그 시간이 0 이다.**

로그로 따라갈 수 있다:
```
[갱신] DART 기업 색인 수집을 시작합니다 (캐시 없음).
[갱신] DART 기업 색인 완료 — …
… 다음 배포 …
[갱신] DART 기업 색인 — 0.3시간 전 자료라 그대로 씁니다.
```

### 알아 둘 것

- **볼륨은 빌드 중에는 안 붙는다.** 런타임 전용이다. 그래서 `npm run build` 에서 수집을
  뺐다 — 거기서 받아 봐야 이미지 안에 남고 볼륨에는 안 들어간다.
  수동으로 받고 싶으면 로컬에서 `npm run fetch-all`.
- **볼륨이 붙은 서비스는 인스턴스를 늘릴 수 없다.** Railway 볼륨은 한 인스턴스 전용이다.
  수평 확장이 필요해지면 캐시를 오브젝트 스토리지나 DB 로 옮겨야 한다.
- **로컬은 아무것도 바꿀 필요가 없다.** `CACHE_DIR` 를 안 주면 예전처럼 `backend/data` 를
  쓴다. 테스트도 그대로 돈다.
- 캐시를 강제로 다시 받게 하려면 볼륨에서 해당 파일을 지우고 재시작한다(없으면 '캐시 없음'
  으로 받는다). 또는 `DAILY_REFRESH_FRESH_HOURS` 를 낮춘다.

## 알려진 것들

- **DB 연결에 실패하면 서버가 뜨지 않는다.** 일부러 그렇게 했다 — 연결이 안 되는데
  포트만 열려 있으면 모든 API 가 500 을 내면서 '살아있는 척' 해서 원인을 찾기 어렵다.
  로그에 `[mysql] 연결 실패 — user@host:port/db` 가 찍힌다.
- **카탈로그를 갱신하려면** 로컬에서 `fetch-*.js` 를 돌려 JSON 을 새로 받은 뒤
  `migrate-to-mysql.js --catalog` 로 배포 DB 에 넣는다. 서버는 직업 분류 트리를
  메모리에 캐시하므로 **재배포(또는 재시작)해야 반영된다.**
- **SQLite 경로는 1차 배포 전에 걷어냈다** (`src/db.js` · `routes/careerData.js` ·
  `database/init-db.js`). 네이티브 모듈이라 빌드에서 컴파일이 필요했다. 되살릴 이유 없다.
- **결제는 테스트 키다.** 실결제로 바꾸려면 토스 계약 후 `live_` 키로 교체한다.
- **세션은 sessions 테이블에 있다.** 재배포해도 로그인이 풀리지 않는다.
